# Технический дизайн-документ: Backend-сервер Pocket Manager (MVP)

## 1. Общая архитектурная концепция

Серверная часть приложения построена на базе современного асинхронного Python-фреймворка **FastAPI**. Архитектура следует классическому паттерну многослойного приложения (Layered Architecture), где логика разделена на уровни работы с базой данных, валидации, безопасности и маршрутизации.
* **СУБД:** В качестве базы данных используется PostgreSQL, подключение к которой конфигурируется через переменные окружения (`DATABASE_URL`).
* **ORM (Object-Relational Mapping):** Взаимодействие с базой данных осуществляется через **SQLAlchemy**, что избавляет от написания сырых SQL-запросов и позволяет работать с таблицами как с объектами Python.
* **Валидация данных:** Выполняется "под капотом" FastAPI с помощью библиотеки **Pydantic**.
* **Безопасность:** Реализована на основе спецификации OAuth2 (Password Bearer Flow) с использованием JWT-токенов (JSON Web Token).

## 2. Структура проекта и ответственность файлов

Кодовая база логически разделена на модули, каждый из которых выполняет свою специфическую задачу:

### 2.1. Конфигурация и База Данных (`database.py`)
Отвечает за подключение к PostgreSQL. Здесь инициализируется SQLAlchemy `engine` и создается фабрика сессий `SessionLocal`.
* Реализована функция-генератор `get_db()`, которая предоставляет изолированную сессию БД для каждого HTTP-запроса и гарантированно закрывает ее по завершении (`finally: db.close()`).

### 2.2. Слой моделей данных (`models.py`)
Описывает структуру таблиц в базе данных. Содержит 4 основные сущности, наследуемые от `Base`:
* **`User`**: Пользователи системы. Хранит email, зашифрованный пароль (`hashed_password`) и роль (`RoleEnum`: Самозанятый, Работник, Менеджер).
* **`Task`**: Задачи. Содержит заголовок, описание и булевый флаг завершенности (`is_completed`). Привязана к пользователю через `ForeignKey("users.id")`.
* **`PomodoroSession`**: Завершенные сессии таймера с указанием времени начала, конца и общей длительности.
* **`SanTestResult`**: Результаты тестов САН (Самочувствие, Активность, Настроение) с временной меткой.
* *Связи:* У пользователя настроены отношения (`relationship`) со всеми остальными таблицами по принципу "Один ко многим", с параметром `cascade="all, delete-orphan"` (при удалении пользователя удалятся все его данные).

### 2.3. Слой DTO и сериализации (`schemas.py`)
Здесь описаны модели Pydantic, которые отвечают за фильтрацию и валидацию данных, приходящих от клиента (Requests) и отправляемых клиенту (Responses).
* Строго типизированы обязательные и необязательные поля (например, `Optional[str]` для описания задачи).
* Во всех `Response`-схемах (например, `TaskResponse`, `SanTestResponse`) используется настройка `model_config = ConfigDict(from_attributes=True)`. Это позволяет Pydantic автоматически "читать" данные из объектов SQLAlchemy и конвертировать их в JSON.

### 2.4. Слой безопасности (`security.py`)
Изолирует всю криптографическую логику и работу с токенами:
* **Хеширование:** Для безопасного хранения паролей применяется алгоритм **bcrypt** с автоматической генерацией "соли".
* **JWT:** При входе генерируется токен (функция `create_access_token`) со сроком жизни, который задается через переменную окружения `ACCESS_TOKEN_EXPIRE_MINUTES`.
* **Авторизация:** Реализована зависимость `get_current_user`, которая извлекает Bearer-токен из заголовка запроса, декодирует его, находит пользователя по `email` в БД и передает его объект в контроллер.

### 2.5. Точка входа и Контроллеры (`main.py`)
Главный файл приложения, инициализирующий экземпляр `FastAPI` и описывающий конечные точки (endpoints) REST API.
* Роуты сгруппированы по смыслу: аутентификация (`/auth`), задачи (`/tasks`), помодоро (`/pomodoro`), тесты (`/san-test`).
* Каждый защищенный эндпоинт использует внедрение зависимостей (Dependency Injection) для получения сессии БД (`Depends(get_db)`) и проверки авторизации (`Depends(security.get_current_user)`).

## 3. Жизненный цикл типичного запроса (Data Flow)

Рассмотрим архитектуру в действии на примере создания новой задачи пользователем (POST `/tasks`):

1.  **Получение запроса:** Клиент отправляет POST-запрос с JSON-телом (содержащим `title` и `description`) и заголовком `Authorization: Bearer <token>`.
2.  **Валидация (Inbound):** FastAPI автоматически пропускает JSON через схему `schemas.TaskCreate`. Если данные неверны, клиент получит ошибку 422 Unprocessable Entity до того, как начнет выполняться бизнес-логика.
3.  **Авторизация:** Срабатывает `Depends(security.get_current_user)`. Из БД извлекается модель пользователя, совершившего запрос.
4.  **Бизнес-логика:** В эндпоинте `create_task` создается объект ORM `models.Task`. В него распаковываются данные из схемы (`**task.model_dump()`), и ему принудительно назначается `user_id=current_user.id`. Это гарантирует, что пользователь не сможет создать задачу от чужого имени.
5.  **Транзакция:** Объект добавляется в сессию (`db.add`), фиксируется в БД (`db.commit()`), а затем обновляется (`db.refresh`) для получения сгенерированного базой ID.
6.  **Ответ (Outbound):** Модель SQLAlchemy возвращается из функции, и FastAPI автоматически пропускает её через `response_model=schemas.TaskResponse`, формируя безопасный JSON для клиента.

## 4. Зоны роста (Архитектурный долг для Этапа 2)

Текущий код сервера отлично работает для MVP, но для дальнейшего развития проекта (подготовки к предрелизной версии) стоит запланировать следующие улучшения:

1.  **Маршрутизация (Routers):** Сейчас все эндпоинты лежат в одном файле `main.py`. С добавлением функционала (роли менеджеров, аналитика, отделы) файл станет слишком большим. Стоит разбить их на отдельные файлы с помощью `APIRouter` (например, `routers/tasks.py`, `routers/auth.py`).
2.  **Миграции БД:** Сейчас таблицы создаются командой `Base.metadata.create_all(bind=engine)`. Это работает только при пустой базе. При изменении структуры таблиц (например, добавлении поля для отдела) данные могут потеряться. Решение — внедрить систему миграций **Alembic**.
3.  **Сервисный слой:** Логика сохранения данных (CRUD) сейчас находится прямо в контроллерах (`main.py`). В классической архитектуре её выносят в отдельные файлы (например, `crud.py` или `services/`), чтобы контроллеры отвечали только за прием и отправку HTTP-запросов.
